# DOCX 原格式保真内容替换

## 核心原则

原始 DOCX 是版式契约。处理目标是“只替换已确认的内容”，不是新建文档、重新排版或把文本批量塞进 Word。先解析原文档的段落、run、样式和 OOXML 关系，再在原结构上做最小修改；格式没有明确变更要求时一律继承原格式。

## 成功路径

### 1. 固定输入边界

- 盘点原始 DOCX、待替换内容、输出目录和文件映射；排除 `~$` 锁文件、临时副本和历史输出。
- 复制原件到新输出目录，记录原件 hash/mtime；绝不覆盖原件。
- 如果内容来源是 Markdown，先按块解析标题、正文、列表、引用、代码、表格和图片，再建立“源块 → DOCX 块”的显式映射。不要按页码或文件名相似度猜章节。

🔴 **STOP 1**：文件、章节、替换范围或图片策略不唯一时，先停在映射确认，不写出结果。

### 2. 解析原始 DOCX

优先使用项目提供的 DOCX CLI/解析脚本读取原文档；必要时用 `python-docx` 和 OOXML 辅助核对。建立段落与 run 的可定位索引，同时记录：

- `pPr`：对齐、首行/左右缩进、行距、段前后距、分页控制和标题层级；
- `rPr`：中西文字体、字号、粗斜体、颜色、字符间距和上/下标；
- `numPr`、表格网格、页眉页脚、分节、图片关系、字段和文档属性。

正文替换只作用于命中的段落或 run。保留未命中的 XML，不清空整篇正文，不重建 `Document()`，不删除 `sectPr`、编号定义、媒体关系或页眉页脚。

### 3. 在原结构上替换内容

- 优先修改已有 run 的文本；跨 run 替换时以原 run 的格式为边界，必要时克隆对应 `rPr`，不把整段压平成一种字体。
- 整段替换前先判断段落是否包含混合格式。单一格式段落可以继承对应正文/标题/引用原型；混合格式段落必须按原 run 边界分段替换并保留各自 `rPr`。新内容无法与原有格式边界无歧义对齐时，停止写入并报告，不用一个“最接近”原型覆盖整段。
- 中英文混排显式保留 East Asia 字体和西文字体；不只设置 `run.font.name`。
- `[1]`、`[2]` 等引用文本先按原文保留；只有在映射规则明确时，才对引用 run 设置或继承上角标属性，不把所有方括号数字都当作引用。
- 保留中文标点、Unicode 长破折号、负号、器件名、网表名、代码 token、表格和图片。Markdown 强调、反引号、链接标记只能在已确定的块边界内清理语法壳。
- 允许的变化只来自替换清单；标题删除、标题级别调整、图片替换等都必须作为显式内容/媒体策略记录。

全局正则替换 DOCX XML、所有 runs 或整篇文本是红灯路径，容易破坏引用、代码、编号重启、中文字体和字面量符号。

🔴 **STOP 2**：首次保存前复核映射、替换命中数、格式策略和输出目录，并确认原件备份可恢复。

### 4. 分层验收

**结构验收**

- `unzip -t` 和 DOCX 解析通过，输出数量/文件名符合映射；
- section、页眉页脚、样式、编号、表格、图片关系和文档属性仍在；
- 命中段落之外的文本和 XML 结构没有无授权变化。

**内容验收**

- 逐块比对替换前后文本，确认只发生清单中的替换；
- 标题顺序、列表嵌套、引用集合、代码 token、Unicode 标点和表格内容正确；
- 检查没有残留 Markdown 标记、断裂 run、重复标题或误删正文。

**视觉验收**

用项目既有渲染 CLI 或 LibreOffice 生成 PDF/PNG，至少检查首页、典型正文页、最深标题层级、列表/引用页、中文与代码混排页、分页转折页和末页。对“看似缺标题、底部空白、旧图残留”等异常，同时核对 PDF 文本、页面图像和 OOXML，不能只依据查看器缩略图判断。

🔴 **STOP 3**：结构、内容或渲染任一层未通过，输出只能标为“未验收草稿”，不得交付。

## 风险处理

- 精确匹配失败或命中数异常：停止该文件，报告上下文和候选位置。
- 字体、行距或缩进漂移：回到原段落 `pPr/rPr` 克隆和 East Asia 字体核对。
- 图片、字段、签章或行政占位与新内容冲突：按已记录策略保留、替换、删除并文字化，或暂停等待确认。
- 渲染器不可用：可以报告结构/文本结果，但明确标注视觉验收未完成。

## 交付报告

列出：输入原件与输出文件、替换映射和命中数、继承的格式/媒体/分节关系、原件 hash/mtime、结构检查、文本检查、渲染检查和剩余风险。只有三层验收全部通过，状态才可写为“已验收”。
